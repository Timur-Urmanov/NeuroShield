# Журнал гипотез

Правило: гипотеза и критерии пишутся **до** запуска. Статистика: 5 сидов (0–4), среднее ± sd (ddof=1).
Сравнение вариантов — **парная** разность по сидам (общие случайные числа: один и тот же поток задач
и `U` на сид). «Эффект есть», если |среднее разности| > 2·sd разности; иначе «эффекта не обнаружено».
Основная метрика `post` = средняя награда за последние 1000 задач из 8000 (после сдвига режима).

## H1. Выигрыш W в среде с ролями выдерживает сравнение с централизованными базовыми линиями

Среда `roles` (clean: без усталости и сна), N=40, доли ролей 1/3. Команда базовых линий — ровно 3.
Базовые линии (`swarm/baselines.py`): выбор модели {LinUCB, оракул} × выбор команды
{соло, случайная, agent-UCB (индивидуальный кредит), pair-UCB (комбинаторный бандит над парами), оракул}.
pair-UCB получает выгодную для себя настройку: c ∈ {0.03, 0.1, 0.3, 1.0}, в сравнение идёт лучший c.

- **Гипотеза:** рой `W_reward` (s=0.5) лучше LinUCB + лучший pair-UCB.
- **Подтверждение:** парная разность post(W_reward) − post(LinUCB+pair-UCB*) > 2 sd.
- **Опровержение:** разность < −2 sd (централизованный бандит лучше) — тогда W остаётся только как
  децентрализованная аппроксимация, а не как источник выигрыша. |разность| ≤ 2 sd — эффекта нет.
- Дополнительно фиксируем потолки: оракул-маршрутизатор + случайная команда, оракул + оракул-команда,
  LinUCB + оракул-команда (сколько теряется на выборе модели), agent-UCB (ожидаем ≈ случайной команде:
  в этой среде у всех примитивов одинаковая маргинальная ценность).

## H2. Вес сходства s в рекрутинге: оптимум внутри интервала

s ∈ {0, 0.25, 0.5, 0.75, 1}, W_reward.
- **Гипотеза:** при s=0 команды не собираются (≈ соло), при s=1 — уровень «только сходство» (≈0.457);
  лучшее s внутри (0, 1).
- **Подтверждение:** лучшее внутреннее s лучше обоих концов больше чем на 2 sd. **Опровержение:** один из
  концов не хуже лучшего внутреннего значения.

## H3. Размер команды 2–5

W_reward, team ∈ {2,3,4,5}. В исходной среде лишний член команды бесплатен, а качество = max по ролям,
поэтому больше людей не может уменьшить q — это дефект среды. Прогоняем при `member_cost` = 0 и 0.05
(штраф за каждого дополнительного члена = ещё один вызов LLM).
- **Гипотеза:** при member_cost=0 награда не убывает с размером; при 0.05 оптимум = 3 (число ролей).
- **Подтверждение / опровержение:** при 0.05 team=3 лучше team=2 и team=5 на >2 sd / не лучше.

## H4. Устойчивость к долям ролей и N

W_reward против «только сходство» (W выключена) и против LinUCB+pair-UCB*:
доли (1/3,1/3,1/3), (0.5,0.25,0.25), (0.6,0.2,0.2), (0.8,0.1,0.1); N ∈ {20, 40, 80} при равных долях.
- **Гипотеза:** преимущество W над «только сходство» сохраняется (>2 sd) во всех условиях.
- **Опровержение:** хотя бы в одном условии разность ≤ 2 sd. Ожидаем, что при редкой роли (0.1) эффект
  ослабнет: дефицитных партнёров мало и они перегружены.

## H5. Хебб с добавкой и прунинг во сне — разные механизмы

Среда `roles` с усталостью и сном (как legacy «full»), Хебб по награде как основа.
2×2: hebb_bias ∈ {0, 0.3} × sleep_prune ∈ {вкл, выкл}.
- **Гипотеза:** оба механизма вредят независимо: (a) прунинг снижает покрытие при bias=0;
  (b) bias снижает награду и при выключенном прунинге.
- **Подтверждение:** каждый из двух главных эффектов > 2 sd. **Опровержение:** один из эффектов ≤ 2 sd —
  тогда в старом выводе «сон с прунингом выбивает связи» вклад приписан не тому механизму.

## H6. Фаза полезна для временной координации (Курамото в среде с порядком шагов)

Среда `ordered`: шаг j (план → исполнение → проверка) выполняет член команды на позиции j;
правильный состав в неправильном порядке ничем не лучше неполного состава.
Состав команды везде одинаковый механизм (W_reward, s=0.5, фазовый фильтр в рекрутинге выключен,
кроме одного варианта). Меняется только механизм упорядочивания:
- `recruit` — лидер, затем по очкам рекрутинга (что рой делает неявно);
- `random` — случайная перестановка;
- `position` — скаляр на примитив, обучаемый правилом «пара a→b раздвигается при dopa>0, сближается/
  меняется местами при dopa<0» (без осцилляторов);
- `phase_static` — то же правило на фазе θ, но без динамики Курамото (контроль: фаза = скаляр на круге);
- `phase_kuramoto` — то же правило + полная динамика Курамото (дрейф ω, связь через W, шум,
  синхронизация успешных команд);
- `phase_kuramoto_filter` — плюс фазовый фильтр в рекрутинге (как в legacy);
- `oracle` — порядок по скрытым ролям (потолок).
- **Гипотеза:** `phase_kuramoto` лучше `position` больше чем на 2 sd.
- **Опровержение:** `phase_kuramoto` ≤ `position` + 2 sd → динамика Курамото не даёт ничего сверх
  обучаемого скаляра; код Курамото удаляется (остаётся только в `legacy/` для воспроизведения).

проверяет то, ради чего нужна децентрализация. Старый вывод «W нужна» верен только относительно
вариантов роя без W, не относительно сильной базовой линии.

## H1b. Когда хорошая команда зависит от задачи и примитивы заняты

Зарегистрировано после H1 и до запуска. Две модификации среды `roles`, 2×2:
- `role_by_type`: сильная роль примитива своя для каждого типа задачи (отдельная перестановка ролей на
  тип; доли 1/3 на каждом типе). Фиксированная тройка больше не оптимальна.
- `busy`: примитив после задачи занят τ=8 шагов (ёмкость; 3·8 = 24 из 40 заняты в среднем). Одна
  тройка физически не может обслужить поток.
Базовые линии те же + **кластерный pair-UCB**: онлайн k-means по x на 3 кластера (бандиту дают знание
числа типов — это выгодно бандиту) и отдельный pair-UCB на кластер. Бандиты видят ту же маску занятости.
c для бандитов — лучший из {0.03, 0.1, 0.3}.
- **Гипотеза:** в клетке (role_by_type, busy) рой W_reward ≥ лучшего бандита (разность > −2 sd), а в
  клетке (нет, нет) воспроизводится H1 (бандит лучше).
- **Подтверждение:** рой лучше лучшего бандита на > 2 sd в клетке (да, да) — W оправдана как
  механизм контекстного состава. **Ничья (|d| ≤ 2 sd):** W эквивалентна сильной базовой линии,
  оставляем как дешёвую децентрализованную альтернативу, но не как источник выигрыша.
  **Опровержение:** бандит лучше на > 2 sd и здесь — W не даёт преимуществ ни в одной проверенной среде.
- Примечание о честности: это вторая среда после проигрыша в первой; результат H1b не отменяет H1 и
  оба идут в итог.

Почему фаза проигрывает: фаза задаёт только **циклический** порядок (a→b→c ≡ b→c→a), «первого» на
круге нет. Правило «раздвинуть a и c» на круге одновременно сближает их через другую сторону, и разрез
(кто первый) перескакивает. Скаляр на прямой этой проблемы не имеет. Динамика Курамото (дрейф частот,
связь через W, шум, синхронизация успешных команд) не меняет результат ни в одну сторону.

**Решение:** код Курамото (θ, ω, фазовый фильтр, фазовая динамика, фазовые порядки) удаляется из
`swarm/core.py`. Воспроизведение старых строк с Курамото — через `legacy/swarm.py` или коммит
до удаления (см. git log). Механизм `order="position"` остаётся флагом: он нужен только в средах, где
важен порядок, и проигрывает порядково-зависимому бандиту так же, как W проигрывает pair-UCB.

## H7. Бонус исследования в рекрутинге закрывает разрыв с pair-UCB

Зарегистрировано до реализации. Причина проигрыша, предложенная в сводке фазы 1: у бандита оптимизм к
непробованным парам, у роя рекрутинг — argsort по W без исследования.

Механизм (флаг `explore`, по умолчанию выключен):
- `ucb`: счётчик совместной работы n[i,j] (симметричный, растёт для всех пар в команде, как W).
  Очки рекрутинга: `(1−s)·W[leader] + s·sim + c·sqrt(log(t+2) / (n[leader]+1))`.
- `noise`: вместо счётчиков — шум в очках, `+ c·|N(0,1)|` (отдельный генератор случайных чисел).
  Это контроль: помогает ли именно направленное исследование или любой разброс.
- Порог `recruit_thr` = 0.25 тот же. Бонус может поднять кандидата над порогом, и средний размер
  команды может вырасти. Размер команды отчитываем.

Протокол (подбор c не на тестовых сидах, в отличие от бандитов в H1/H1b):
1. Подбор: c ∈ {0.02, 0.05, 0.1, 0.2, 0.4} для каждого из `ucb` и `noise` на сидах 100–104, в клетке
   «роли общие, без занятости». Выбираем лучший c по post.
2. Тест: выбранный c на сидах 0–4 во всех четырёх клетках H1b. Сравнение с W_reward без бонуса и с
   лучшим бандитом (результаты бандитов — из `results/h1b_context_capacity.json`; там c подобран
   на тестовых сидах, это выгодно бандиту).
3. Дополнительно: среда ordered с `order=position`, сравнение с seq-UCB из H6.

- **H7a (бонус помогает):** `ucb` лучше W_reward без бонуса на > 2 sd минимум в 3 из 4 клеток.
- **H7b (паритет с бандитом):** в клетке, где H7a выполнена, разность «рой+ucb − лучший бандит» > −2 sd.
- **H7c (направленность):** `ucb` лучше `noise` на > 2 sd минимум в 2 из 4 клеток.
- **Опровержение H7a:** эффект в ≤ 2 клетках. Тогда причина проигрыша не в исследовании.

## H8. W как средний успех пары закрывает разрыв с pair-UCB

Флаг `w_rule`, 2×2 «оценка × сигнал», чтобы развести два фактора:
- `hebb_r` (текущее): W += 0.5·η·(r − EMA₃₀(r)), клип [0,1], затухание ×(1−0.0005);
- `hebb_succ`: то же, но сигнал = succ − EMA₃₀(succ) (без стоимости модели);
- `mean_r`: W[a,b] = (Σ r + W₀[a,b]) / (n + 1) по командам, где a и b были вместе; без затухания;
- `mean_succ`: то же по succ — оценка как у pair-UCB, но без бонуса исследования (H7: он не нужен).
W₀ — исходная случайная W (U(0, 0.2)) как априорное значение с весом одного наблюдения.
Свободных параметров нет, подбора нет; сиды 0–4, четыре клетки H1b. Бандиты — из
`results/h1b_context_capacity.json`.

- **H8a:** `mean_succ` лучше `hebb_r` на > 2 sd минимум в 3 из 4 клеток.
- **H8b:** в этих клетках `mean_succ` − лучший бандит > −2 sd (паритет).
- **Атрибуция (описательно):** вклад оценки = среднее (mean_* − hebb_*), вклад сигнала =
  среднее (*_succ − *_r) по клеткам.
- **Опровержение H8a:** эффект в ≤ 2 клетках.
